# Native ML-DSA-44 (experimental post-quantum profile)

The toolkit has one native post-quantum signature experiment: ML-DSA-44 from
[NIST FIPS 204](https://csrc.nist.gov/pubs/fips/204/final), assigned to scheme `0x03`
inside the patched FrameTx implementation.

> [!CAUTION]
> This is a **non-normative toolkit-local allocation**. Upstream EIP-8141 reserves `0x03`.
> An upstream or otherwise unpatched client rejects these transactions, and a future
> upstream scheme may conflict with this encoding. The implementation is experimental,
> has not been independently audited, and must not protect production funds.

Unlike WebAuthn, ML-DSA-44 verification happens in the native transaction validator before
any frame executes. There is no ML-DSA EVM precompile and the Solidity contracts never see
or parse the signature bytes. They receive only protocol-verified scheme, signer, and
message metadata through `SIGPARAM`.

The exact local protocol delta is specified in
[`spec/EIP8141.md`](../../spec/EIP8141.md#toolkit-local-ml-dsa-44-scheme-0x03-non-normative).

## Exact entry and signer identity

An authorizing entry has:

| Entry field | Required value |
|---|---|
| `scheme` | `0x03` (toolkit-local `ML_DSA_44`) |
| `signer` | Empty only when the derived key identity equals `tx.sender`; otherwise the explicit 20-byte identity below |
| `msg` | Empty when authorizing the complete frame transaction |
| `signature` | `sigma || publicKey`, exactly 3,732 bytes |

FIPS 204 fixes the ML-DSA-44 sizes:

| Object | Bytes |
|---|---:|
| Encoded private key | 2,560 |
| Encoded public key | 1,312 |
| Encoded signature `sigma` | 2,420 |
| Toolkit native wire `sigma || publicKey` | 3,732 |

The public key is carried in every entry because ML-DSA does not recover it from a
signature. Its EVM-facing identity is domain-separated from every other native scheme:

```text
mldsaSigner = address(low160(keccak256(0x03 || publicKey)))
```

The leading byte is exactly one byte, not the ASCII string `"0x03"` and not an ABI-encoded
integer. In Solidity the matching expression is:

```solidity
address(uint160(uint256(keccak256(abi.encodePacked(bytes1(0x03), publicKey)))))
```

The node compares this identity with the entry's resolved signer. An empty `signer` resolves
to `tx.sender`; an explicit signer must be exactly 20 bytes.

## Message and canonical decoding

The verifier uses FIPS 204 **pure ML-DSA** with an empty context. It supplies the existing
32-byte FrameTx message directly as the FIPS message byte string; it does not use
HashML-DSA and does not prehash that value again.

- Empty `msg` selects `compute_sig_hash(tx)`. Account and paymaster authorization requires
  this case because it commits to the sender, nonce, fees, frames, and selected-index
  calldata.
- A non-zero, exactly 32-byte `msg` is valid at protocol level but signs only that explicit
  digest. The example contracts reject it for transaction authorization.
- A 32-byte zero digest and every other length are invalid.

The raw field has one encoding. The decoder:

1. requires exactly 3,732 bytes;
2. splits bytes `0..2419` as the 2,420-byte FIPS signature and bytes `2420..3731` as the
   1,312-byte public key;
3. applies the FIPS 204 ML-DSA-44 key and signature decoders;
4. rejects non-canonical forms, including repeated or non-strictly increasing hint indices;
5. checks `low20(keccak256(0x03 || publicKey)) == resolved_signer`; and
6. performs pure-mode verification with `ctx = ""` over the selected 32-byte message.

There is no ABI envelope, DER form, length prefix, alternate public-key representation, or
accepted trailing byte. Corrupting the signature or public key, changing the message or
signer, using a short/long field, or supplying a non-canonical signature rejects the whole
transaction before frame execution.

The host pins RustCrypto
[`ml-dsa 0.1.1`](https://github.com/RustCrypto/signatures/tree/master/ml-dsa). The crate's own README
warns that it has never been independently audited. Version `0.1.1` is newer than the fix
for
[GHSA-5x2r-hc65-25f9](https://github.com/RustCrypto/signatures/security/advisories/GHSA-5x2r-hc65-25f9),
which affected versions through `0.1.0-rc.3` by accepting repeated hint indices. That fixed
advisory does not remove the crate's broader audit warning or audit this integration.

## Gas and transaction size

The local verifier charges a provisional **50,000 gas per ML-DSA-44 entry**. This is
separate from the intrinsic charge for carrying the exact 3,732-byte native wire
field and from the EIP-7623 calldata floor. A wallet must account for both:

- signature-verification gas consumes the validation-prefix budget; and
- the signature/public-key bytes consume transaction bandwidth, intrinsic data gas, and
  calldata-floor tokens.

Under the current `MAX_VERIFY_GAS = 100,000` public-mempool rule, one ML-DSA-44 signature
plus one secp256k1 signature costs `50,000 + 2,800 = 52,800` before frame code, leaving at
most **47,200 gas** for the hybrid multisig validation prefix. Two ML-DSA-44 entries consume
the full 100,000 before any VERIFY-frame code executes, so such a transaction is not
public-mempool eligible under that limit even if it is otherwise executable through direct
or private inclusion. The toolkit does not yet implement the draft public-pool policy, so
local acceptance is not evidence of relay eligibility.

The 50,000 value is a benchmark placeholder, not an upstream gas proposal. The large native
wire is likewise intentional for this experiment: there is no state-backed public-key alias
in the current profile.

## Dedicated account

[`MLDSAAccount.sol`](../src/accounts/MLDSAAccount.sol) is a rotatable single-key account:

| API | Behavior |
|---|---|
| `constructor(bytes publicKey)` | Requires exactly 1,312 bytes and stores the derived signer identity |
| `validate(uint256 signatureIndex)` | Requires the selected canonical scheme-`0x03` entry from `mldsaSigner`, then approves the current non-zero allowed scope |
| `setMLDSAKey(bytes publicKey)` | Replaces the identity; callable only from a SENDER self-call (`msg.sender == address(this)`) |
| `signerForKey(bytes publicKey)` | Requires the exact public-key length and returns `low20(keccak256(0x03 || publicKey))` |
| `mldsaSigner()` | Returns the currently trusted identity |
| `receive()` | Accepts ETH for self-payment or payment for another sender |

The contract stores only the 20-byte identity, not the 1,312-byte key. Each native
transaction still carries the full public key so the node can verify it. Key rotation should
be a current-key-authorized transaction with a SENDER frame targeting the account's
`setMLDSAKey` selector. Once that frame commits, the old identity stops authorizing; keep a
tested recovery path before rotating a key.

Like the other reusable accounts, it derives approval scope from its VERIFY frame and
supports validating and paying for itself (`BOTH`), validating while a later paymaster pays
(`EXECUTION`), and paying for another already-approved sender (`PAYMENT`). The last role is
valid in the EVM, but this storage-backed key policy reads outside `tx.sender` when serving
as another account's payer and therefore violates the generic public-pool storage rule.

## Dedicated paymaster

[`MLDSAPaymaster.sol`](../src/accounts/MLDSAPaymaster.sol) authorizes third-party payment
with one immutable ML-DSA-44 key identity:

| API | Behavior |
|---|---|
| `constructor(bytes sponsorPublicKey, uint256 maxSponsoredCost)` | Requires a 1,312-byte key, derives `sponsorSigner`, records `owner`, fixes the cap, and accepts initial ETH |
| `sponsorTransaction(uint256 signatureIndex)` | Requires the selected canonical scheme-`0x03` entry from the sponsor, enforces the cost cap and exact PAYMENT scope, then approves |
| `signerForKey(bytes publicKey)` | Returns the scheme-domain-separated identity after an exact-length check |
| `owner()` / `sponsorSigner()` / `maxSponsoredCost()` | Return immutable policy values |
| `withdraw(address payable to, uint256 amount)` | Owner-only withdrawal |
| `receive()` | Accepts sponsorship funding |

The sponsor key is deliberately immutable; rotate it by deploying a new paymaster. This is
not the upstream canonical paymaster runtime, so the draft's non-canonical paymaster limits
apply. Its immediate withdrawal is also unsuitable for a shared public paymaster because it
can invalidate pending transactions.

## Generic native-signer support

The dedicated contracts enforce the exact algorithm. The toolkit's generic address-policy
examples intentionally work with any supported protocol-validated signer identity:

| Contract | Scheme behavior |
|---|---|
| `OwnerAccount` | Rejects `ARBITRARY`; secp256k1, P256, or ML-DSA-44 may authorize when the resolved signer equals `owner` |
| `SessionKeyAccount` | Rejects `ARBITRARY`; any of the three native schemes may identify its owner or a registered session key |
| `account.yul` / `account-builtins.yul` | Reads `resolved_signer` directly, so all three native schemes work; `ARBITRARY` exceptional-halts |
| `MultisigAccount` | Explicitly admits secp256k1, P256, and ML-DSA-44 owner entries in one threshold set |

Configure these policies with the ML-DSA key identity, not with a public key or an unrelated
Ethereum EOA address. Mixed-algorithm multisig works because each native verifier exposes the
same 20-byte identity interface after its own cryptographic check.

Algorithm-specific examples remain strict:

- `P256Account` and `P256Paymaster` accept only native `P256` scheme `0x02`;
- `WebAuthnAccount` and `WebAuthnPaymaster` accept only their exact `ARBITRARY` scheme
  `0x00` assertion profile and still execute P256VERIFY in contract code; and
- `SponsoringPaymaster` accepts only `SECP256K1` scheme `0x01`.

Adding scheme `0x03` does not silently reinterpret a P256 or WebAuthn credential.

## Default EOA payment and multisig signature reuse

The protocol's empty-code default account remains **secp256k1-only**. A codeless address
cannot validate or pay with scheme `0x03`, even if that address equals an ML-DSA key
identity. Post-quantum authorization needs `MLDSAAccount`, another compatible account, or a
delegation to such code unless the default-code specification changes.

A separate secp256k1 optimization is valid today. Suppose a codeless secp256k1 owner is also
an owner of the transaction sender's `MultisigAccount` and will pay for that transaction:

1. Put that owner's canonical, empty-`msg` `SECP256K1` entry at signature index **1**, with
   its explicit 20-byte signer address.
2. Include index `1` in the multisig execution frame's `validate(uint256[])` calldata so it
   counts toward threshold, respecting the multisig's ascending-signer order.
3. Place a later PAYMENT-only VERIFY frame against that codeless owner. Default code selects
   index `1` for PAYMENT and accepts the same entry.

There is one envelope entry and one `v || r || s` value over `compute_sig_hash(tx)`, not a
second signature. Both validators reuse the same canonical authorization. Replacing that
entry with ML-DSA-44 does not work for the payer frame because empty-code default validation
requires `SECP256K1`.

## Test boundaries

`MLDSAAccountTest` inherits `AccountTestSuite`, so the dedicated account is exercised in all
three approval roles, with shifted routing, wrong-selection, exact-scope, key-rotation, and
funding cases. `MLDSAPaymasterTest` inherits `PaymasterTestSuite`; like the secp256k1, P256,
and WebAuthn paymaster tests, it must sponsor every account target, including
`MLDSAAccount`, from a dynamically shifted scalar signature index.

Those Solidity tests use `setFrameTx` metadata that represents signatures already verified
by the host. They prove contract policy and routing, not ML-DSA cryptography. The Rust
transaction tests generate a real ML-DSA-44 key and signature and cover canonical success,
wrong hash/signer, corrupted key/signature, non-canonical encoding, wrong length, and the
50,000-gas assignment.

The raw Anvil suite then installs the production `MLDSAAccount` runtime, submits a real
3,732-byte scheme-`0x03` envelope, and keeps native verification plus declared VERIFY-frame
execution at **95,000 gas**. It first corrupts the signature and proves admission rejection
without a nonce or SENDER effect; the valid envelope is mined with the account as payer and
checks its ETH debit, sender-nonce increment, and later SENDER write.

A second raw regression exercises the secp256k1 reuse layout above. Its two secp256k1
verifications and two VERIFY-frame budgets total **65,600 gas**. The mined receipt names the
index-1 multisig owner as payer, the multisig nonce advances, the operation executes, and the
codeless payer owner's own account nonce remains unchanged.
