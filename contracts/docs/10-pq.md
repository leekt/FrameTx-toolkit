# Post-quantum signatures through `ARBITRARY`

EIP-8141 currently defines three signature schemes:

| Scheme | Meaning |
|---|---|
| `0x00` | `ARBITRARY`: witness bytes validated by frame execution |
| `0x01` | Protocol-validated secp256k1 |
| `0x02` | Protocol-validated P256 |
| `0x03`–`0xff` | Reserved |

The toolkit follows that allocation exactly. It does not assign `0x03` to ML-DSA and does
not ship a native ML-DSA verifier, ML-DSA account, or ML-DSA paymaster.

## How an ML-DSA experiment fits Frame transactions

An application that wants ML-DSA should encode its complete proof material in the
`signature` bytes of an `ARBITRARY` entry. The outer entry must use scheme `0x00` and an
empty `signer`; the protocol performs only the structural checks required for
`ARBITRARY`. A `VERIFY` frame then:

1. checks that the selected entry uses `SCHEME_ARBITRARY`;
2. requires the empty-`msg` case and reads the canonical hash with `TXPARAM(0x08)`;
3. obtains the witness length with `SIGPARAM(0x03)`;
4. copies the witness with `SIGDATACOPY`;
5. parses and verifies the application's chosen ML-DSA profile against that hash; and
6. calls `APPROVE` only after the proof and account policy both succeed.

The proof must be bound to the canonical Frame transaction signature hash when it authorizes
the transaction. A verifier should also define its ML-DSA parameter set, context handling,
public-key encoding, signature encoding, canonical-decoding rules, and the exact way the
account stores or derives the trusted key identity. Those choices are application policy,
not EIP-8141 signature-scheme semantics.

## Current implementation boundary

There is no ready-to-use ML-DSA verifier in this repository. In particular, the toolkit
does not currently define:

- a canonical `ARBITRARY` witness ABI for ML-DSA;
- an EVM contract or precompile that performs ML-DSA verification;
- an ML-DSA account or sponsoring paymaster;
- a native signer identity derived by the transaction validator; or
- a protocol verification gas charge for ML-DSA.

Witness calldata, memory expansion, and validation-frame execution still consume their
ordinary transaction and EVM gas. Public-mempool eligibility also remains subject to
EIP-8141's validation-prefix limits and opcode restrictions. Until a concrete verifier is
implemented and benchmarked, this documentation makes no gas or transaction-size claim.

## Pure-function validation direction

A future pure-function validation mechanism could execute a verifier without state access,
cache its result across state changes, and let L2s recognize or replace known verifier code
with optimized implementations. That direction avoids allocating a protocol signature
scheme for every new cryptographic algorithm: ML-DSA witness bytes could remain
`ARBITRARY`, while a dedicated pure frame or verifier contract supplies the structured
cryptographic check.

Pure verification does not replace account authorization. A stateful validation frame must
still decide whether the verified public key or credential is accepted by the account and
which approval scope it grants.

## Testing requirements for a future verifier

Any future ML-DSA example should include at least one successful end-to-end authorization
and explicit refusal cases for malformed encodings, wrong keys, wrong messages, non-canonical
encodings, and truncated or oversized witnesses. These are expected-failure assertions: the
test itself passes only when account or paymaster validation fails closed.

[`09-p256-and-webauthn.md`](09-p256-and-webauthn.md) demonstrates the current supported
pattern for a non-native authenticator: carry a bounded `ARBITRARY` witness, reconstruct the
signed message in account code, call an available cryptographic verifier, and approve only
after policy checks succeed.
